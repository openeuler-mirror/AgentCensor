# 策略编写与保护范围

要保护目录和数据，优先用 `file` 约束实际文件操作；要禁止某个程序或明确的
参数前缀，用 `exec`。当前参数规则不解析命令选项的含义，不提供 glob 或正则匹配。
完整配置、发布和纳管步骤见 [使用手册](使用手册.md)，实际验收见
[手动测试指南](手动测试指南.md)。

## 按保护目标选择规则

| 保护目标 | 规则示例 | 生效位置 |
| --- | --- | --- |
| 目录及内容允许读取、禁止修改 | `file deny+audit /srv/important [write,delete,rename,attr]` | 文件操作时检查目标及祖先目录 |
| 禁止读取某个文件 | `file deny+audit /srv/important/secret.txt [read]` | 打开或读取目标文件时检查 |
| 禁止启动某个程序 | `exec deny+audit /usr/bin/rm` | 执行实际可执行文件时检查 |
| 禁止一个确定的子命令或参数前缀 | `exec deny+audit /usr/bin/git push` | 执行时按位置比较参数 token |

这些约束只适用于**已纳管的进程树**，对应 `enable_file` / `enable_exec` 必须开启。
全局基线和域绑定的全部组叠加生效，任一层 deny 即拒绝；未命中规则默认放行。
`+audit` 要求命中时上报，不改变匹配范围。

## 用 file 保护目录及其内容

```yaml
rules:
  - file deny+audit /srv/important [write,delete,rename,attr]
```

该规则在文件操作的检查点约束目录及其子孙，允许读取，拒绝写入、删除、改名及属性
修改。换用不同 `rm` 参数、Python 或其它工具，不会取消这些文件操作约束。
因此，要保护的是数据时，应直接声明受保护路径，不必枚举所有可能修改它的命令。
若还需要禁止读取，可加入 `read`，或省略掩码以拒绝全部支持的文件操作。

**发布规则前先确保目标目录存在。** 编译器会建立目录 inode 身份，内核通过祖先目录
检查覆盖内部内容，无需写 `/srv/important/*`。目录不存在时只保留路径回退，不能
将其当成已经建立递归保护；创建或重建目录后，附加组重新 `policy apply`，基线则
重新加载 daemon。文件检查点和路径解析的其它边界见 [使用手册](使用手册.md)。

执行命令与操作文件是两个不同检查点。例如只禁止读取秘密文件时，`cat` 应正常
启动并产生 **EXEC ALLOW**，随后读取秘密文件产生 **FILE DENY**。
若 `cat` 本身出现 EXEC DENY，应检查执行规则，而不是将其视为文件规则的正常结果。

## exec 参数规则是按位置匹配完整 token 的前缀

```yaml
rules:
  - exec deny+audit /usr/bin/rm -rf /
```

策略行按空白分词，`exec` 和 `deny+audit` 不计入匹配 token；上例得到：

```text
["/usr/bin/rm", "-rf", "/"]
```

程序身份通过实际可执行文件 inode 和路径规则判断，参数则逐个比较位置与内容。
规则必须从第一个参数开始匹配；完整规则序列是实际执行序列的前缀时才命中。
这里的“前缀”指 **token 序列**，不是单个 token 的字符串前缀：`push` 不匹配
`push-other`，`-rf` 不匹配 `-r`。

下面仅说明这条 exec 规则的匹配结果，不表示这些写法都能成功删除文件；其它执行
规则、文件规则、系统权限和程序自身的检查仍可能拒绝操作。

| 实际执行的参数写法 | 是否命中上例 | 原因 |
| --- | --- | --- |
| `rm -rf /` | 是 | 参数位置及内容一致 |
| `rm -rf / 后续参数` | 是 | 追加参数不改变已匹配的前缀 |
| `rm -r -f /` | 否 | 两个独立 token 不等于 `-rf` |
| `rm -fr /` | 否 | 不做短选项顺序归一化 |
| `rm -rf -- /` | 否 | `--` 改变了目标参数的位置 |
| `rm --force --recursive /` | 否 | 不理解长短选项的等价关系 |

`exec deny /usr/bin/rm` 没有参数，禁止整个程序的执行；但它不会禁止其它程序删除
文件。参数规则适合明确的前缀限制，不能代表对某类危险行为的完整识别。

## token 的数量、长度和分词限制

- **数量**：每条参数规则最多 4 个 token，即程序路径 + 前 3 个参数。这是当前
  实现上限；YAML 决定该规则实际使用几个 token，超过上限会报错。运行时命令可以
  有更多参数，但第 4 个及之后的参数不进入匹配窗口；增加参数数量不会自动扩大窗口。
- **长度**：每个规则 token 最长 255 字节，按 UTF-8 字节计算；超过上限明确报错。
  它是项目限制，不是 Linux 完整路径或执行参数的系统最大值。
- **运行时长参数**：不会把截短内容当成一个较短的完整 token。即使后续参数很长，
  已经匹配的拒绝前缀仍有效；这不代表等价选项变体也会命中。
- **审计**：展示程序路径和前 3 个参数，每个 token 最多 255 字节；审计 args
  不是完整命令行存档。
- **分词**：规则解析使用空白分词，不是 shell 解析器；加 YAML 引号也不能让含空格
  的内容自动变成一个匹配 token。不提供 shell 引号、转义、变量或通配符展开。

重复同一条规则不会增加匹配窗口或覆盖范围。单纯提高 token 数量也不能解决
`-rf` 与 `-r -f` 等等价选项的识别问题；那需要另行实现命令选项规范化。

## 通配符与默认 DSH 示例的边界

当前 **file 和 exec 都没有 glob 匹配功能**。例如：

```yaml
rules:
  - exec deny+audit /usr/bin/rm -rf /*
```

其中 `/*` 是字面量 token。通过 shell 执行命令时，shell 通常会先将 `/*` 展开为
`/bin`、`/etc` 等多个参数；内核收到的是展开后的 argv，因此不会命中这个字面量
规则。文件名模式 `/srv/important/*.key` 也不能当作现有的通配符规则使用。

即使以后加入参数通配符，`/*` 的定义也需要明确：是否跨越路径分隔符、是否覆盖
任意绝对路径等。若匹配所有绝对路径，也可能误拦 `rm -rf /tmp/test`；通配符仍
不会自动处理选项拆分、参数重排或匹配窗口之外的目标。

默认 [DSH 示例策略](../config/policy.dsh-default.yaml) 提供特定命令/参数的黑名单，
其中 `rm -rf /`、`rm -rf /*` 等行不能解释为“已覆盖所有等价的危险删除命令”。
部署时应为实际重要目录补充 `file` 规则，再以 exec 规则限制特定工具和子命令。
按文件名模式保护和按命令含义判断危险操作都属于尚未实现的能力。

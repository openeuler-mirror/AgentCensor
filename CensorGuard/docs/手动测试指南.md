# CensorGuard 0.5.0 手动测试

约 5 分钟。需要两个终端，以下命令从 **CensorGuard 仓库根目录**开始执行。
使用独立测试组和 `/tmp` 文件，不修改现有 DSH 策略。

## 1. 安装并确认服务

```bash
make setup
sudo censorguardctl status
```

预期显示 `Ready`、`BPF hooks Healthy`，以及 `/etc/censorguard/base.yaml`。
`make setup` 已启用并启动服务，无需再执行 `systemctl enable --now`。
若要查看 ALLOW 审计，确保该文件 `daemon` 下三个 `audit_*` 为 `true`；修改后执行：

```bash
sudo censorguardd reload --config /etc/censorguard/base.yaml
sudo censorguardctl status
```

## 2. 准备文件和测试策略（终端 A）

```bash
mkdir -p /tmp/cg-manual-050
printf 'public\n' > /tmp/cg-manual-050/public-with-a-long-name.txt
printf 'secret\n' > /tmp/cg-manual-050/ro-secret-with-a-long-name.txt
printf '#!/bin/bash\nprintf "script-ok\\n"\n' > /tmp/cg-manual-050/ok.sh
chmod +x /tmp/cg-manual-050/ok.sh
cat > /tmp/cg-manual-050/policy.yaml <<'YAML'
rules:
  - file deny+audit /tmp/cg-manual-050/ro-secret-with-a-long-name.txt [read]
  - exec deny+audit /usr/bin/echo blocked
YAML
sudo censorguardctl policy apply --policy cg-manual-050 --file /tmp/cg-manual-050/policy.yaml
sudo censorguardctl bind --domain cg-manual-050 --policy cg-manual-050
sudo censorguardctl status
```

apply/bind 预期分别显示 `Policy applied` / `Policy bound`，apply 回执包含源文件绝对路径。
status 中应看到 `cg-manual-050 [configured; no processes]` 及其策略文件路径，启动前 `Managed 0` 正常。
脚本验证时可给 apply/bind 加 `--json`，检查 `ok: true`、`daemon_ready: true`。
全局基线仍叠加生效；组内没有某条规则，不代表它没有被基线或其它绑定组拒绝。

## 3. 观察审计（终端 A）

```bash
sudo censorguardctl audit
```

该终端保持运行。文件加载产生多条 ALLOW 正常。只检查拦截结果可换成：

```bash
sudo censorguardctl audit --domain cg-manual-050 --result deny
```

`--kind exec`（兼容 `--kind 2`）只显示执行检查，**看不到文件读取/删除的 DENY**。
cat 启动成功、随后读取 secret 失败时，EXEC ALLOW 与 FILE DENY 会有相同 PID，
这不表示策略失效。用 `--kind file` 看文件拒绝，或保持全类型观察。

## 4. 进入受控 shell 并逐条测试（终端 B）

```bash
sudo censorguardctl spawn --domain cg-manual-050 -- bash --noprofile --norc
```

以下命令在刚打开的受控 shell 内执行；`--noprofile --norc` 避免本机启动脚本干扰测试。

```bash
cat /tmp/cg-manual-050/public-with-a-long-name.txt
cat /tmp/cg-manual-050/ro-secret-with-a-long-name.txt
/usr/bin/echo allowed
/usr/bin/echo blocked
/usr/bin/echo blocked a-very-long-argument-that-is-more-than-31-bytes
/usr/bin/echo a-very-long-argument-that-is-more-than-31-bytes
/tmp/cg-manual-050/ok.sh
```

| 操作 | 预期结果 | 关键审计 |
| --- | --- | --- |
| cat public | 输出 `public` | EXEC ALLOW、FILE ALLOW |
| cat ro-secret | cat 启动成功，但读取报 `Operation not permitted` | EXEC ALLOW、目标 FILE DENY |
| echo allowed | 输出 `allowed` | EXEC ALLOW |
| echo blocked | shell 报 `Operation not permitted` | EXEC DENY |
| echo blocked + 长参数 | 仍拒绝，不可绕过前缀规则 | EXEC DENY |
| echo 单个长参数 | 正常输出 | EXEC ALLOW；展示参数可能截短 |
| ok.sh | 输出 `script-ok` | 脚本/解释器检查均放行 |

必须写 `/usr/bin/echo`，裸 `echo` 是 shell 内建命令，不触发 exec 检查。
参数规则按**完整 token 的前缀序列**匹配；`blocked` 不匹配 `blocked-other`，`/*` 也不是通配符。
规则每个 token 最长 **255 字节**（按 UTF-8 字节计算），包含程序路径在内最多 4 个 token。
超长规则发布时报错；运行时超长参数不会误匹配截短后的 token，已命中的拒绝前缀仍生效。
参数审计每个 token 最多展示 255 字节。该上限是项目限制，并非 Linux 完整路径/参数的系统上限。

## 5. 验证策略更新

先在终端 A 按 Ctrl+C 结束审计，再执行：

```bash
printf 'rules: []\n' > /tmp/cg-manual-050/policy.yaml
sudo censorguardctl policy apply --policy cg-manual-050 --file /tmp/cg-manual-050/policy.yaml
sudo censorguardctl status
```

终端 B 再执行读取 secret 和 `/usr/bin/echo blocked`，两者应正常输出。
只保存组 YAML 不会更新已发布策略，必须重新 apply；本步骤无需重启 daemon。

## 6. 结束并清理

终端 B 执行 `exit` 回到原 shell；终端 A 执行：

```bash
sudo censorguardctl remove --domain cg-manual-050 --policy cg-manual-050
sudo censorguardctl policy remove --policy cg-manual-050
sudo censorguardctl status
rm -r /tmp/cg-manual-050
```

本测试的进程树应已退出；其它 DSH 进程仍可保持纳管。
服务由 systemd 管理时，停止使用 `sudo systemctl stop censorguardd.service`；
同时取消开机启动使用 `sudo systemctl disable --now censorguardd.service`。
手动 `launch` 的实例使用 `sudo censorguardd stop --config PATH`，随后可用同一路径重新 launch。

# openEuler 24.03 LTS SP3（aarch64）目标主机离线部署指南

本文说明在目标主机安装 CensorGuard 核心组件的过程。依赖准备、源码构建、离线部署包生成和
校验清单由准备机完成，目标主机从解包校验开始。

目标主机流程为：解包并校验离线部署包、检查环境并补齐运行依赖、安装文件和启动服务、按阶段
加载配置。前四步可由离线部署包内的 `tools/cg-deploy.sh` 一条命令完成（第 2 节），也可按
第 3 节分步执行；操作人员依据部署前检查报告处理环境后再继续。

部署初始配置采用：`failure_mode: permissive`、`self_protection: false`、空规则、
普通审计关闭、`dsh_enabled: false`、`spawn_grpc: false`。先确认服务稳定，再逐条发布
经部署方确认的 `deny` 规则。

## 1. 离线部署包解包与校验

本指南以 openEuler 24.03 LTS SP3 aarch64 为例。以部署用户身份在自己主目录下解包，
与准备机使用同一路径约定 `$HOME/CensorGuard`：

```bash
cd /path/to/media
sha256sum -c CensorGuard-aarch64.tar.gz.sha256
export CG_OFFLINE="$HOME/CensorGuard"
mkdir -p "$CG_OFFLINE"
tar -xzf CensorGuard-aarch64.tar.gz -C "$HOME"
cd "$CG_OFFLINE"
sha256sum -c SHA256SUMS
```

`CG_OFFLINE` 在同一个 shell 中设置。后续 `sudo` 命令里的路径由它在当前 shell 展开为
绝对路径后再交给 `sudo`，路径展开在部署用户的 shell 中完成；以 root 直接登录时 `$HOME`
是 `/root`，两种情况按各自的登录方式取路径。部署用户主目录需对 root 可读（默认 `0700`、
属主为部署用户时 root 仍可读取）。重复解包会合并覆盖同名文件，需要干净环境时先清空
`$CG_OFFLINE`。

解包后的目录内容：

```text
rpms/runtime/                                                目标主机运行库及传递依赖
keys/                                                        RPM 签名公钥
release/rootfs/                                              目标主机安装文件树
release/CensorGuard-standalone-aarch64.tar.gz                二进制
tools/check-deployment-env.sh                                  只读环境检查器
tools/cg-deploy.sh                                           一键部署编排脚本
records/                                                     RPM、工具链、构建和校验记录
docs/                                                        本指南与配套文档
SHA256SUMS                                                   部署文件校验清单
```

文档集中在 `docs/` 目录，随离线部署包分发。
`docs/` 中另有 `部署环境检查.md`（检查器参数与报告字段）、`策略编写与保护范围.md`
（规则写法与边界）。

安装完成后目标主机使用的核心文件：

```text
/usr/sbin/censorguardd
/usr/bin/censorguardctl
/usr/lib/censorguard/enforce.bpf.o
/etc/censorguard/base.yaml
/usr/lib/systemd/system/censorguardd.service
/usr/lib/sysusers.d/censorguard.conf
/usr/lib/tmpfiles.d/censorguard.conf
```

## 2. 一键部署（推荐）

`tools/cg-deploy.sh` 把第 3 节的四个步骤串成一条命令：环境检查 → 补齐运行依赖 →
安装文件与初始配置 → 启动并验证。脚本按检查结论分派：随包有候选 RPM 的缺失项执行
验签和安装，其余缺失项写入报告并给出处理方式；内核、启动参数、`sysctl` 和挂载相关项
按第 2.4 节的形式给出操作指引。

### 2.1 运行

前提是已按第 1 节完成解包与校验，`CG_OFFLINE` 在当前 shell 中已设置。

```bash
sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" all
```

先查看将要执行的动作，演练模式只打印命令：

```bash
sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" all --dry-run
```

脚本按自身位置推导离线部署包根目录（`<离线部署包>/tools/cg-deploy.sh`）。把脚本单独拷到其他
位置运行时，用 `--kit "$CG_OFFLINE"` 显式指定。

其余选项：`--out 目录`（报告目录）、`--log 文件`、`--yes`（自动确认常规提示）、
`--skip-verify`（省略离线部署包校验）、`--force`（重新执行安装）。完整说明见
`sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" --help`。

### 2.2 子命令与执行内容

| 子命令 | 执行内容 |
| --- | --- |
| `check` | 调用离线部署包内的检查器采集环境并生成报告（只读采集） |
| `fix` | 对 `MISSING` 项逐包 `rpm -K` 验签 → `dnf --assumeno` 预览 → 确认后安装 → 自动复查 |
| `install` | 解包文件树、建系统用户与目录、生成初始配置、`--check-config`、启动并检查套接字 |
| `all` | `check` → `fix` → 复查 → `install` |

`install` 面向首次安装，执行前确认两项：最近一次检查无 `BLOCK` 和关键 `UNKNOWN`，
`/usr/sbin/censorguardd` 尚未存在。已安装环境按升级变更流程单独处理；需要在已安装环境
重新执行时加 `--force` 直接进入安装。

安装事务中若出现 glibc、systemd、kernel、openssl-libs 等基础组件变更，脚本会单独警示
并要求逐字输入 `yes` 确认。这类变更影响整机，需部署方确认并留存回退方案。

### 2.3 部署后的服务状态与配套操作

1. 脚本以 `systemctl start` 启动服务，服务在当前启动周期内运行；需要随主机自启时由部署方
   确认后单独执行 `sudo systemctl enable censorguardd.service`。
2. 内核启动参数、`sysctl`、挂载和 `/etc/fstab` 按第 2.4 节的指引执行。
3. 业务进程接入、策略发布和阶段配置加载按第 3.4 节和第 4 节执行。
4. `/etc/censorguard/base.yaml` 已存在时保留原文件内容。首次安装从预制模板复制生成该活动
   配置，后续规则增删会回写这份副本；切换阶段前按第 4 节备份并合并已有修改。

若 `censorguardd.service` 已设为开机启动，脚本在摘要中提示，关闭命令为
`sudo systemctl disable censorguardd.service`。

### 2.4 内核与系统配置类缺失

`CONFIG_*`、`active-lsm`、`btf`、`lsm-hooks`、必需 tracepoint、只读挂载、`cgroup`、
`bpf_jit_enable` 等项由系统配置处理，脚本在终端和 `deploy-summary.md` 中按
"现状 / 处理 / 生效 / 复核"四段给出处理方式。三类常见的：

- **活动 LSM 没有 bpf**：属启动期参数，需在启动命令行配置。执行
  `sudo grubby --update-kernel=ALL --args="lsm=...,bpf"`，`lsm=` 的取值
  与 `/sys/kernel/security/lsm` 现有列表保持一致、只在末尾追加；改动前备份
  `/boot/loader/entries`，重启后生效。
- **tracefs 未挂载**：`sudo mount -t tracefs tracefs /sys/kernel/tracing` 后立即生效；
  持久化在 `/etc/fstab` 增加条目，由部署方决定。
- **部署目录只读或 noexec**：由系统管理员调整 `/etc/fstab` 并在维护窗口内 remount。

凡需重启或改引导的操作，按部署变更流程在维护窗口执行。

### 2.5 单独执行某一步

```bash
sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" check      # 环境体检并出报告
sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" fix        # 补依赖，装完自动复查
sudo bash "$CG_OFFLINE/tools/cg-deploy.sh" install    # 装文件并启动，要求 check 已通过
```

常见用法是先用 `check` 生成报告，确认后再执行 `all`，或者 `fix` + `install`。

### 2.6 产物与退出码

报告目录默认 `/var/tmp/cg-deploy-check`，可用 `--out` 改：

```text
cg-deploy.log                                全过程日志
deploy-summary.md                            部署摘要
transaction-preview.txt                      最近一次安装事务预览
check/deployment-environment-report.txt        部署环境报告
check/deployment-operation-report.txt        缺失及处理报告
check/findings.tsv                           机器可读结论
check/previous/<时间戳>/                      安装前那一轮报告（自动保留）
```

退出码：`0` 通过；`1` 参数错误；`2` 存在阻断性缺失；`3` 存在关键待确认项或需人工
确认；`4` 安装阶段失败。返回 `2` 或 `3` 时按摘要处理后重跑同一条命令即可。

`deploy-summary.md` 与两份报告一并保留在部署变更记录中。

## 3. 分步部署（对照与排障）

一键部署已覆盖本节全部步骤。需要逐步复现、排障，或部署方要求逐条确认时按本节执行；
两条路径的产物与判定标准一致。

### 3.1 部署环境检查

解包后先记录部署环境及缺失。
目标主机还必须具备发行版基础库、动态加载器、systemd、RPM/DNF、归档工具和运行服务所需的内核能力。
检查器还会分析两个用户态 ELF 的实际 `NEEDED` 库、BPF 对象、默认库路径、systemd 工具和随包 RPM
候选项。检查器逐项采集本机状态、部署产物和随包 RPM 元数据，最终在 `--output` 指定的目录生成两份文件：

```bash
sudo bash "$CG_OFFLINE/tools/check-deployment-env.sh" \
  --output /var/tmp/cg-deployment-check
```

`--output` 为必填项，报告目录由操作人员指定；未指定时脚本返回参数错误（返回码 `2`）。

部署产物默认按离线部署包相对路径识别：脚本位于 `<离线部署包>/tools/`，自动使用
`release/rootfs/usr/sbin/censorguardd`、`release/rootfs/usr/bin/censorguardctl`、
`release/rootfs/usr/lib/censorguard/enforce.bpf.o`、
`release/rootfs/etc/censorguard/base.yaml.example` 和 `rpms/runtime`。
报告首部的 `input:` 与 `input-source:` 记录每个部署产物最终使用的路径及其来源
（`auto` 自动识别、`explicit` 显式指定）。自动识别失败时，报告列出已查找的路径并
要求用对应选项指定，例如：

```bash
sudo bash "$CG_OFFLINE/tools/check-deployment-env.sh" \
  --output /var/tmp/cg-deployment-check \
  --daemon "$CG_OFFLINE/release/rootfs/usr/sbin/censorguardd" \
  --ctl "$CG_OFFLINE/release/rootfs/usr/bin/censorguardctl" \
  --bpf-object "$CG_OFFLINE/release/rootfs/usr/lib/censorguard/enforce.bpf.o" \
  --config "$CG_OFFLINE/release/rootfs/etc/censorguard/base.yaml.example" \
  --rpm-dir "$CG_OFFLINE/rpms/runtime"
```

再次对同一目录执行同一命令时，脚本替换该目录中上一轮的同一组报告；
需要保留历史记录时加 `--keep-previous`，上一轮报告会移到
`<目录>/previous/<时间戳>/`。目录内其他文件保持原样；若该目录非空且不是本脚本生成的
目录，脚本保留其内容并提示改用其他路径。

查看 `/var/tmp/cg-deployment-check/deployment-environment-report.txt` 了解目标主机的实际环境，
查看 `/var/tmp/cg-deployment-check/deployment-operation-report.txt` 获取后续操作建议。
第二份报告逐项列出缺失及处理方法：`BLOCK` 为阻断性缺失，包括运行内核能力不足和
必需依赖缺失且随包没有候选包；`MISSING` 为随包有候选 RPM 可补齐；`UNKNOWN` 为证据
不足。脚本正常生成报告就返回 `0`，环境问题只在报告中体现。

检查器同时把每条结论写成机器可读清单（`--findings` 指定路径，省略时写到
`<output>/findings.tsv`；五列：状态、键、是否必需、描述、候选包）。`cg-deploy.sh`
按它分派自动安装与人工处理；人工阅读仍以两份报告为准。

操作人员据此决定后续动作：出现阻断性缺失时，按报告给出的处理方式处理，完成后重新检查；
随包可补齐的依赖先核验并预览事务，部署方确认后安装；信息不足时按报告补充工具或证据。
处理完成后重新执行同一条检查命令复查（需要保留每轮记录时使用 `--keep-previous`），
再按本指南部署。两份报告保留在部署变更记录中。

`readelf`（`binutils`）和 `bpftool` 等用于部署诊断，与上述四个运行库包分开准备。
若目标主机缺少这些工具，报告会标明证据不足；应在准备机通过 DNF 下载相应包及依赖，补充到
离线仓库后重新分发。基础部署工具缺失时按报告一并补齐，再继续部署。

检查脚本的参数、报告字段和采集边界见 [部署环境检查](部署环境检查.md)。

### 3.2 安装运行依赖

使用本地 runtime 仓库安装运行依赖。先导入验签公钥并检查随包 RPM，这两步完成材料校验：

```bash
sudo rpm --import "$CG_OFFLINE/keys/RPM-GPG-KEY-openEuler"
find "$CG_OFFLINE/rpms/runtime" -name '*.rpm' -exec rpm -K {} \;
```

确认 RPM 签名有效后，先预览安装事务。`--assumeno` 解析依赖并显示将要变更的包：

```bash
sudo dnf --disablerepo='*' \
  --repofrompath="cg-runtime,file://$CG_OFFLINE/rpms/runtime" \
  --enablerepo=cg-runtime --setopt=cg-runtime.gpgcheck=1 \
  --setopt=cg-runtime.repo_gpgcheck=0 \
  --setopt=install_weak_deps=False \
  install --assumeno libbpf elfutils-libelf zlib libgcc
```

操作人员确认事务内容后，去掉 `--assumeno` 执行实际安装：

```bash
sudo dnf --disablerepo='*' \
  --repofrompath="cg-runtime,file://$CG_OFFLINE/rpms/runtime" \
  --enablerepo=cg-runtime --setopt=cg-runtime.gpgcheck=1 \
  --setopt=cg-runtime.repo_gpgcheck=0 \
  --setopt=install_weak_deps=False \
  install libbpf elfutils-libelf zlib libgcc
```

安装请求仍只列出四个运行库包，其传递依赖由 DNF 自动求解。事务可能包含库升级或其它包变更，
以预览结果为准；安装完成后，再执行一次第 3.1 节的检查命令，复核动态库及符号版本兼容性。
同一目录会被覆盖为最新一轮结果，需要保留安装前那轮报告时，安装前那次检查加
`--keep-previous`，或安装后再检查时加该参数把上一轮归档。

上面两条命令覆盖"运行库"这一最小集合。若第 3.1 节的报告还把诊断工具（如 `binutils`、
`bpftool`）列为 `MISSING`，按报告给出的候选包一起装；`cg-deploy.sh fix` 按 `MISSING`
项逐个安装，并在安装前对每个候选包执行 `rpm -K`。

### 3.3 安装文件和初始配置

以下为首次安装流程，执行前确认环境处于未安装状态（服务未运行、状态目录为空）。
解包安装文件树：

```bash
sudo tar -C / -xzf "$CG_OFFLINE/release/CensorGuard-standalone-aarch64.tar.gz"
sudo systemd-sysusers /usr/lib/sysusers.d/censorguard.conf
sudo systemd-tmpfiles --create /usr/lib/tmpfiles.d/censorguard.conf
sudo install -d -m 0750 -o root -g censorguard /etc/censorguard /var/lib/censorguard
sudo test -e /etc/censorguard/base.yaml || \
  sudo install -m 0640 -o root -g censorguard \
    /etc/censorguard/base.yaml.example /etc/censorguard/base.yaml
sudo systemctl daemon-reload
```

`base.yaml.example` 是预制模板，`base.yaml` 是部署时实际使用和维护的副本。
服务固定读取 `/etc/censorguard/base.yaml`；日常操作使用这份活动配置，保留 `.example`
和 `stages/` 下的预制文件供对照、回退，避免直接以模板路径启动 daemon。
`rule append/remove` 会回写运行实例启动时使用的配置文件，并规范化 YAML 格式、移除注释，
因此应先复制模板再使用。复制命令只在 `base.yaml` 不存在时创建副本，已有文件保持原样。

配套 systemd unit 已将 `/etc/censorguard` 加入 `ReadWritePaths`，以允许 daemon 在同一目录
创建临时文件并原子替换活动配置。升级已有服务时需安装配套 unit、执行
`systemctl daemon-reload` 并重启服务，使该目录的写权限生效；仅执行 `rule apply` 不会更新
systemd 的文件系统限制。

确认配置包含以下初始值：

```yaml
daemon:
  dsh_enabled: false
  spawn_grpc: false
  failure_mode: permissive
  self_protection: false
  enable_file: true
  enable_exec: true
  enable_net: true
  audit_file: false
  audit_exec: false
  audit_net: false
rules: []
```

配置检查：

```bash
sudo /usr/sbin/censorguardd launch \
  --config /etc/censorguard/base.yaml --check-config
```

### 3.4 启动空规则并开始观察

```bash
sudo systemctl start censorguardd.service
sudo systemctl status censorguardd.service --no-pager
sudo censorguardctl doctor
sudo censorguardctl status --json
```

`cg-deploy.sh` 执行到 `systemctl start` 为止。需要随主机自启时，由操作人员确认后单独执行
`sudo systemctl enable censorguardd.service`；保持当前启动周期运行时，重启后由操作人员
重新启动服务。

确认以下 socket 存在：

```text
/run/censorguard/ctl.sock
/run/censorguard/events.sock
/run/censorguard/launch.sock
```

#### 3.4.1 发现目标进程

纳管前先查看进程列表，确认要接入的业务进程、所属用户和启动命令：

```bash
ps -eo pid,ppid,user,comm,args
```

根据部署环境确认目标进程树的根 PID。不要仅凭进程名判断，需核对可执行文件路径、
启动参数和所属用户，避免接入无关进程。以下以 `12345` 作为示例根 PID：

```bash
sudo readlink -f /proc/12345/exe
sudo cat /proc/12345/cmdline | tr '\0' ' '
```

#### 3.4.2 接入纳管

将 `12345` 替换为实际根 PID，`example-app` 替换为用于标识该业务的 domain 名称：

```bash
sudo censorguardctl attach --pid 12345 --domain example-app
```

目标进程退出并重新创建后，应重新确认根 PID 并执行接入命令。若需要自动接入，
可在进程启动或服务编排流程中调用 `censorguardctl attach`；策略发布与 domain 绑定应在
接入前完成并确认。

空规则阶段确认业务运行、纳管关系和资源开销；三个 `audit_*` 保持 `false`，
后续通过规则的 `+audit` 记录命中行为。

## 4. 按阶段加载配置并逐步打开拦截

离线部署包在 `/etc/censorguard/stages/` 提供四份预制的完整启动配置：每份都包含
完整的 `daemon` 段和该阶段生效的全部基线规则。先校验模板，再复制到活动配置
`/etc/censorguard/base.yaml`，以这份副本运行；配置调整都保存在活动配置中。

阶段按影响面由小到大推进：先观察、再文件、再网络、最后执行。执行拒绝按 token 精确
匹配，对业务启动命令的影响面最大，放在最后一级。

| 执行顺序 | 文件 | 相对上一阶段新增的默认规则 |
| --- | --- | --- |
| 4.1 | `deployment-01-observe.yaml` | 观察基线：`/etc/shadow`、`/etc/gshadow`、`/etc/sudoers` 读取，`ssh`/`scp`，出站 22/443，全部 `allow+audit` |
| 4.2 | `deployment-02-file-deny.yaml` | `/etc/shadow`、`/etc/gshadow` 拒绝全部文件操作；`/etc/sudoers` 拒绝读取 |
| 4.3 | `deployment-03-net-deny.yaml` | 拒绝出站 23（telnet）、21（ftp） |
| 4.4 | `deployment-04-exec-deny.yaml` | 拒绝 `nc`、`ncat`、`socat`、`telnet` 及 `rm -rf /` |

文件名中的 `01`～`04` 与加载顺序一致：观察 → 文件拒绝 → 网络拒绝 → 执行拒绝。

预制规则需结合业务核对后加载。需要增加经部署方确认的保护项时，在活动配置的 `rules`
下调整，或使用第 4.5 节的命令增删。手工编辑时每行一条规则，说明写在上一行；
规则按空白分词，行内文字会被当作参数。

每次切换阶段前，先备份当前活动配置：

```bash
sudo cp -a /etc/censorguard/base.yaml \
  "/etc/censorguard/base.yaml.backup.$(date +%Y%m%d-%H%M%S-%N)"
```

下面的 `install` 会用阶段模板完整替换活动配置，包括此前由 `rule append/remove` 保存的
修改。已有自定义规则或 daemon 设置需要保留时，先根据备份核对并合并到活动副本，再校验和
加载；不要把这些修改写回预制模板，也不要直接覆盖而丢失已有配置。

这些规则是 daemon 的全局基线，作用于所有已纳管 domain。阶段文件先覆盖活动配置
`/etc/censorguard/base.yaml`，再以该路径作为 `censorguardd reload --config` 的参数：
运行中的 daemon 要求 reload 路径与启动路径一致。
每个阶段都按同一组步骤执行：校验阶段文件 → 覆盖固定的活动配置 → reload → 复查健康 →
重新纳管业务 → 核对业务行为。

### 4.1 进入观察阶段

```bash
sudo /usr/sbin/censorguardd launch \
  --config /etc/censorguard/stages/deployment-01-observe.yaml --check-config
sudo install -m 0640 -o root -g censorguard \
  /etc/censorguard/stages/deployment-01-observe.yaml /etc/censorguard/base.yaml
sudo censorguardd reload --config /etc/censorguard/base.yaml
sudo censorguardctl doctor
sudo censorguardctl attach --pid 12345 --domain example-app
sudo censorguardctl audit
```

`12345` 是示例根 PID，按第 3.4.1 节确认实际业务根 PID 后替换；`example-app` 替换为
实际 domain 名称，下面三个阶段相同。确认事件中出现上述观察项的命中，且业务运行与资源开销
正常后，再进入下一阶段。

### 4.2 增加文件拒绝

```bash
sudo /usr/sbin/censorguardd launch \
  --config /etc/censorguard/stages/deployment-02-file-deny.yaml --check-config
sudo install -m 0640 -o root -g censorguard \
  /etc/censorguard/stages/deployment-02-file-deny.yaml /etc/censorguard/base.yaml
sudo censorguardd reload --config /etc/censorguard/base.yaml
sudo censorguardctl doctor
sudo censorguardctl attach --pid 12345 --domain example-app
```

复查业务读写是否正常，并核对事件中 `FILE DENY` 只出现在预期路径上。

### 4.3 增加网络拒绝

```bash
sudo /usr/sbin/censorguardd launch \
  --config /etc/censorguard/stages/deployment-03-net-deny.yaml --check-config
sudo install -m 0640 -o root -g censorguard \
  /etc/censorguard/stages/deployment-03-net-deny.yaml /etc/censorguard/base.yaml
sudo censorguardd reload --config /etc/censorguard/base.yaml
sudo censorguardctl doctor
sudo censorguardctl attach --pid 12345 --domain example-app
```

只涉及出站 23 和 21 两个端口，业务侧确认没有 telnet、ftp 类依赖后再进入下一阶段。
若业务确有 ftp 传输，先与操作人员确认豁免方式，再进入执行拒绝阶段。

### 4.4 增加执行拒绝

```bash
sudo /usr/sbin/censorguardd launch \
  --config /etc/censorguard/stages/deployment-04-exec-deny.yaml --check-config
sudo install -m 0640 -o root -g censorguard \
  /etc/censorguard/stages/deployment-04-exec-deny.yaml /etc/censorguard/base.yaml
sudo censorguardd reload --config /etc/censorguard/base.yaml
sudo censorguardctl doctor
sudo censorguardctl attach --pid 12345 --domain example-app
```

这是本指南示例流程的最后一个阶段。业务中若确有程序需要启动上面被拒绝的命令，先确认豁免需求，
再从活动副本 `/etc/censorguard/base.yaml` 删除对应行，并执行 `censorguardctl rule apply`；
`exec` 规则按 token 位置匹配规则前缀，参数变体需要分别核对。
完成后再核对一轮业务连通性，并把四轮报告和事件记录归档。

每次 reload 都会完整重启 daemon 并清空 PID 纳管关系，因此上面每个阶段的 `attach` 都要
执行。若使用进程启动或服务编排流程自动接入，reload 后也需重新接入仍在运行的目标进程。
`deny` 规则在对应 `enable_file`、`enable_exec` 或 `enable_net` 开启时产生拦截；
`failure_mode: permissive` 下，路径解析、参数采集等内部检查失败按放行处理。若只需要对单个
domain 增加规则，使用 `policy apply` 发布附加组并用 `bind` 绑定，全局阶段配置保持原样。
需要回退时，用同一组命令重新加载上一个阶段的文件即可。

### 4.5 日常增删全局规则

完成阶段部署后，直接维护活动副本，操作前按本节前面的命令备份。以下为操作示例，
替换为经部署方确认的实际规则：

```bash
sudo censorguardctl rule append 'file deny+audit /srv/example/secret [read]'
sudo censorguardctl rule remove 'file deny+audit /srv/example/secret [read]'
sudo censorguardctl rule apply
sudo censorguardctl status --json
```

前两条命令演示添加后删除同一条规则；每次增删立即保存到 `/etc/censorguard/base.yaml`，
此时当前拦截行为不变。`rule apply` 将活动配置中保存的全部全局规则热更新到所有已纳管
进程树，无需重启或重新 attach；即使没有执行 apply，下次启动也会自动加载已保存的增删。
重复添加不产生副本，删除不存在的规则报错；删除全局规则不会删除附加组内的同类规则。

`status --json` 显示当前生效规则，尚未 apply 的修改以活动 YAML 为准。
`rule apply` 只加载全局规则，`daemon` 设置仍需通过 `censorguardd reload` 完整重启。
后续切换阶段或回退时，先备份并核对这份活动副本中的自定义修改。
